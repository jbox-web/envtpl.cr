## 3. Error model


## Hypothèses vérifiées et écartées

- **`envtpl -i f -o f` (même fichier) corromprait la source.** Non : `convert` lit et rend intégralement avant d'appeler `File.write` (`src/envtpl.cr:96-99`) ; une erreur de rendu laisse la cible intacte (vérifié : sortie vers un répertoire inexistant → exit 1, cible non touchée).
- **Une erreur de rendu écraserait la cible avec du vide.** Non : `File.write` n'est jamais atteint en cas d'exception (vérifié sur template invalide, exit 1 sans écriture).
- **`with_env` fuirait des variables entre exemples.** Non : `ENV[key] = nil` supprime réellement la clé (sonde compilée), et le `ensure` couvre le cas d'exception.
- **`{% include %}` permettrait une traversée `../` ou un chemin absolu.** Non : le `FileSystemLoader` de crinja refuse les deux (vérifié) ; seul le sous-arbre du CWD est accessible.
- **`Hash#select(keys)` lèverait sur une clé absente dans `env('FOO','BAR')`.** Non : les clés manquantes sont silencieusement ignorées et l'ordre demandé est préservé (`{{ env('AAA','BBB') }}` → `{}`, vérifié) — conforme aux specs.
- **`rm -rf bin/*` supprimerait `bin/.keep`.** Non : le glob shell n'inclut pas les fichiers cachés (vérifié).
- **`alpine:3.24` n'existerait pas (tag inventé).** Si : le tag est publié sur Docker Hub (vérifié via l'API).
- **Les actions GitHub seraient épinglées sur des majeurs périmés.** Non : `checkout@v7`, `mise-action@v4`, `setup-qemu-action@v4`, `setup-buildx-action@v4`, `release-action@v1` sont les majeurs courants (`gh api …/releases/latest`).
- **`Crinja.render` recompilerait le template à chaque variable.** Non : un seul parse par exécution, le programme ne rend qu'un template.
- **`STDOUT.puts` doublerait la newline d'un contenu déjà terminé par `\n`.** Non : `IO#puts` ne l'ajoute que si elle est absente (vérifié) — c'est précisément ce qui masquait le défaut COR-src/envtpl.cr:106 sur STDOUT.
- **Le `COPY .git/` du `Dockerfile` ferait fuiter des identifiants dans l'image publiée.** Non : `.git/` ne vit que dans l'étage `build-binary-file` ; les cibles `binary-file` (scratch) et `docker-image` (distroless) ne copient que le binaire. Reste un coût de cache (invalidation à chaque commit), pas un défaut de sécurité.
- **Le job `ameba` de CI serait vide faute de `bin/ameba`.** Non : `mise dev:deps` (`shards install`) construit l'exécutable ameba avant l'étape d'analyse ; l'exécution locale confirme 4 fichiers inspectés, 0 échec.
